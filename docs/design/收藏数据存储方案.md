# 收藏数据存储方案（服务器存储成本 ≈ 0）

> 为《记忆教练-收藏管道设计》设计存储：目标是**"我（开发者）的服务器不存用户媒体文件"**，云存储压力全部推到"用户自有的免费云盘 + 免费第三方层"上，自己的服务器只做极小职责（甚至为零）。
> 原则一句话：**照片进"用户自己的云盘/本地"，字迹进"免费小库"，服务器的硬盘一块都不给收藏数据。**

## 一、设计目标与约束

| 约束 | 含义 |
| --- | --- |
| 服务器存储趋近 0 | 媒体文件 100% 不上自己服务器 |
| 利用现有资源 | 架构文档已有本地 SQLite + 轻量服务器/Supabase，全部复用，不引入新付费依赖 |
| 数据不丢 | 至少有一层"可恢复"备份（本地 + 用户云盘 / 导出） |
| 体验不裂 | 跨设备用户能拿到自己的收藏（用户云盘路线）；单设备用户零门槛 |
| 隐私 & 版权 | 照片默认私有；剪藏只存引用 |

## 二、存储分层总览

```
┌──────────────────────────────────────────────────────┐
│ L1 本地（App 沙盒 + SQLite）—— 一切的主战场             │
│   照片压缩版/元数据/AI产物/日志   离线可用，秒开        │
└──────────────┬───────────────────────────────────────┘
               │ 备份 / 同步（用户授权后）
┌──────────────▼───────────────────────────────────────┐
│ L2 用户自有云盘（零成本给开发者）                       │
│   iCloud Drive（iOS 内置，用用户配额）                  │
│   WebDAV（坚果云等，国内用户）  /  Google Drive（出海）   │
└──────────────┬───────────────────────────────────────┘
               │ 仅此三类小数据
┌──────────────▼───────────────────────────────────────┐
│ L3 服务器免费层（Supabase 免费档 / 自建轻量服务器）       │
│   只存：账号 + 索引 + 分享海报 + 复习日志文本             │
│   （媒体文件永不进入 L3）                                │
└──────────────────────────────────────────────────────┘
```

## 三、四大数据类别归属

| 数据类别 | 体积量级 | 存放层 | 说明 |
| --- | --- | --- | --- |
| 媒体文件（照片/截图） | 100~500KB/张（压缩后） | **L1 本地 + L2 用户云盘** | 原图可选只留本地；云盘放压缩版 |
| 收藏元数据（条目/分类/时间/链接） | 0.5~2KB/条 | L1 + L2（JSON 小文件） | 剪藏只存引用+链接，不托管原文 |
| AI 成卡产物（词条/卡面/音频） | 词条 1KB；卡面 50~200KB | L1；词条去重并入本地词库 | 音频复用官方离线包/系统 TTS，不存新文件 |
| 交互数据（复习日志/打标/成就） | 0.1~0.5KB/条 | L1 + L3（免费层） | 服务端只收文本日志（架构文档既定） |
| 分享产物（名片/海报） | 临时 200~500KB | 本地生成 → 第三方免费图床/免费 B2 | 短链 + 海报本体不占自己服务器 |

> 结论格局：**自己服务器上只会有"文字"（日志 + 索引 + 昵称），照片一张都不过门。**

## 四、本地层设计

### 4.1 文件目录

```
<App Sandbox>/museum/
  media/       压缩后照片（1280px / 质量 70% → 100~300KB）
  originals/   原图（可选保留，仅本地，不备份）
  clips/       剪藏引用快照（标题+URL+摘要，无正文）
  export/      一键导出 zip 的临时目录
<SQLite>/museum.db   收藏条目 / 分类 / 复习日志 / AI 产物
```

### 4.2 体积控制三板斧

1. **拍摄即压缩**：收藏入口处同步压缩（1280px、70% 质量），原图默认丢弃、可选保留本地——照片体积立降 80%+。
2. **剪藏只存引用**：标题 + URL + 首句摘要（<1KB），全文不上传——版权 + 体积双赢。
3. **指纹去重**：同一图片重复收藏只存一份 + 两条收藏记录；AI 卡面按词条指纹复用（与官方词库命中即引用官方卡，不去重生成）。

## 五、用户云盘层（零成本的核心）

> 这是"不让我承担服务器存储"的关键答案：**复用用户自己已经付费的云盘**。开发者成本 = 0，存储配额 = 用户的。

### 5.1 三条路线（按平台/用户选择）

| 路线 | 适用 | 技术路径 | 开发者成本 |
| --- | --- | --- | --- |
| **iCloud Drive** | iOS 主力（国内 iCloud 用户量可观，苹果配额随用户付费） | App 启用 iCloud entitlements；记忆教练备份目录放入 iCloud Drive 容器（文件提供者/UIDocument），Flutter 经 file 通道读写 | **0** |
| **WebDAV** | 国内 Android / 自选（坚果云免费 1GB、腾讯微云等） | 标准 WebDAV 协议（dav 客户端库），用户填账号点授权即可；设定"仅 Wi-Fi 备份" | **0** |
| **Google Drive / Dropbox App 文件夹** | 出海版本 | Drive API 的 app-specific folder（只读自己文件夹） | 0（API 配额免费） |

### 5.2 同步策略（用户云盘上有什么）

```
museum_backup/
  items_YYYYMMDD.json    收藏元数据全量快照（增量合并，<2MB/万条）
  media/                 压缩照片（与本地 media 同名对应）
  museum.zip（可选）      用户手动一键导出
```

- **写入时机**：Wi-Fi + 充电时自动增量备份；收藏动作即时写一个"待备份"标记。
- **恢复**：新设备 → 登录云盘 → 选择"从备份恢复"（首次全量，之后增量）。
- **无账号用户**：纯本地模式（L1），提供手动导出 zip 兜底——单设备用户不受影响。

## 六、服务器免费层（极小职责）

| 职责 | 量级 | 载体 |
| --- | --- | --- |
| 账号与设备绑定 | 几十字节/人 | Supabase Auth（免费档 50k MAU）或自建 JWT |
| 复习日志文本（用于多端合并） | 0.1~0.5KB/条/日 | Supabase Postgres 免费 500MB 或自建轻量服务器 |
| 分享索引（资产统计卡海报短链 → 指向海报 URL） | 1KB/条 | 同上 |
| 公共服务（词库版本、软著、隐私政策） | 静态 | 自建轻量服务器（架构文档 50~100 元/月已含） |

> **铁律：L3 永远不加"文件上传接口"**——从架构上杜绝媒体文件进入自家服务器。

## 七、多设备同步矩阵（三档）

| 档位 | 用户场景 | 数据流 | 服务器成本 |
| --- | --- | --- | --- |
| A 单设备（默认） | 不登录、不用云盘 | 全在 L1，手动导出 zip | **0** |
| B 云盘同步 | 登录 iCloud/WebDAV | 媒体+元数据走 L2 用户云盘；日志走 L3 | **0（占用户配额）** |
| C 全同步（账号） | 用账号 + 云盘 | A/B + 日志云端 → 多端回放（架构文档既定机制） | Supabase 免费档内 |

> 产品建议默认 A/B：**登录非必需**，云盘是"锦上添花"，避免任何一步挡住"拍下第一张收藏"。

## 八、数据导出与所有权

- **一键导出**："导出我的收藏库" → zip（media + items.json + 导出日期），本地生成、走系统分享。
- **导出内容**：压缩照片、元数据、词条文本、复习统计——全部机器可读（JSON）。
- **删号即删**：用户删除账号 → 删除 L3 索引与日志；L2 用户云盘里的备份由用户自己删（产品需说明）。
- 设计立场：**数据所有权在用户侧**，也是"服务器零存储负担"的推论之一。

## 九、成本核算

以 1 万 DAU、人均 200 收藏、每张照片压缩后 200KB 估算：

| 项 | 传统"全上服务器" | 本方案 |
| --- | --- | --- |
| 照片存储 | 200KB × 200 × 1万 ≈ **400GB → ~500~1500 元/月** | 0（用户云盘/本地） |
| 元数据 | 1KB × 200 × 1万 ≈ 2GB → 存储费若干 | 0（本地 + 用户云盘） |
| 备份与 CDN | 备份副本 + 流量 ≈ 1000+ 元/月 | 0 |
| L3 文本与索引 | — | Supabase 免费档内（<500MB），**0** |
| **月合计** | **2000~3500 元+** | **0 元（自建轻量服务器 50~100 元/月已覆盖）** |

> 结论：**即使做到 10 万 DAU，只要执行"媒体不进服务器"的铁律，收藏模块的服务器存储成本始终 ≈ 0。**

## 十、安全隐私与版权

- 照片默认私有：仅本机可见；只有用户主动分享"单张或名片"才对外（分享用一次性短链，可过期）。
- 云盘备份由用户自己的账户加密权限保护（iCloud/WebDAV 的既有安全边界），App 不额外收集。
- 剪藏只存引用链接与摘要，不托管全文（版权红线，沿用既有设计）。
- 敏感照（如证件类）提示"不入云盘，仅在本地"——可提供"此件不上云"的隐私标记。

## 十一、风险与权衡

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 国内 iCloud/WebDAV 使用率不均 | 部分用户只有 L1（单设备） | A 档完全可用；导出 zip 兜底；WebDAV 覆盖坚果云等 |
| 云盘授权门槛吓退新手 | 首次收藏中断 | 收藏/复习与云盘完全解耦（B 是后台可选项，不强制） |
| 用户换账号/注销麻烦 | 恢复受阻 | "从备份恢复"向导 + 导出文件可解析 |
| 剪藏链接失效 | 藏品变空壳 | 保存首句摘要 + 打开时回源校验，失败给提示并保留备注 |
| 免费层配额膨胀（日志） | 超 500MB | 日志按 90 天滚动归档到用户云盘；控制单日文本量 |

---

## 结论

> **一句话方案：照片压到 200KB 进"用户的云盘"，字面数据进"免费层"，到 10 万用户时自己的服务器硬盘占用依然为 0。**
> 成本不是算出来的，是**架构上排除掉的**——只要 L3 没有文件上传接口，收藏模块就永远不欠服务器一块硬盘。
> 落地顺序：先 A 档（纯本地 + 导出）上线 → 接 iCloud/WebDAV 做 B 档 → 有数据后再加 C 档账号与分享。
